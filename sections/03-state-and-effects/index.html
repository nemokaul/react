Core Definition & Architectural Role

You already know how to keep state in a component with `useState`, how to push it down with props, and how to share it across a subtree with `useContext`. That triangle covers a lot of apps. It starts to creak in three places: 1. The state has to live at the top of the tree, so every component in between re-renders when the value changes (unless you split contexts or memoize carefully). 2. The state only exists inside React. Anything outside React, a browser event listener, a WebSocket callback, a `setInterval`, has to reach back through a hook to read or update it. 3. The provider needs to wrap every consumer. A second copy of the same app (a second modal root, a second storybook story, a route-level sub-tree) needs its own provider, with its own state.

🧠Under-The-Hood Mental Model

A store that lives outside React is the right answer when state has to survive the absence of a component (a WebSocket handler that updates the chat when the chat panel is unmounted), when the same state has to be read by a worker or a non-React widget, or when a second tree needs its own copy without rebuilding the provider tree. The class of bug this prevents is "the value in the sidebar does not match the value in the URL bar because one reads a stale prop and the other reads a stale context". With Zustand, both read the same store, both update it the same way, and there is no second copy to drift.

Key Code / CLI Example
import { create } from "zustand";

const useCounterStore = create((set) => ({
  count: 0,
  inc: () => set((state) => ({ count: state.count + 1 })),
}));
⚠️Common Pitfall & Production Gotcha

Direct DOM mutation or impure side effects during the render phase cause hydration mismatches, duplicate executions in Strict Mode, and stale closures. Always declare full dependency arrays in useEffect and never read state during render from outside the component tree.

📝Comprehensive Study Notes & Mental ModelQuick Review
Expand NotesCollapse
Core Definition & Architectural Role

Picture a checkout clerk with a quick visual scan. They look at each item on top of each basket. If every item on top matches, they stamp the baskets "equal" and move on. They do not open sealed jars, check brand names underneath, or compare prices stamped on the bottom of a coupon. `shallow` is that clerk: it checks top-level properties only and lets nested objects keep their own identity. This matters because Zustand decides whether to re-render a subscriber by comparing two snapshots. The default check is `Object.is`, which only returns true when both sides are the same reference. When a selector returns a fresh wrapper object on every render, `Object.is` always says "different", and React schedules a new render. `shallow` lets you tell Zustand "check the top-level fields instead; the wrapper is fine if its contents are unchanged".

🧠Under-The-Hood Mental Model

Zustand has no Context and no Provider. Subscribers read directly from the store, and the store uses a comparator to decide whether each subscriber's slice has changed. The comparator is the entire performance model. `Object.is` is the cheapest possible check, and it is what you want for scalar values and stable references. The moment a selector returns a composite slice, you need a comparator that walks one level into it. `shallow` is that comparator. You will see `useShallow` everywhere a real Zustand app selects more than one field, especially around `combine` reducers, derived selectors that return `{ x, y }`, and time-travel features (the tic-tac-toe walkthrough in the reference section below). The same pattern shows up under different names in other libraries: `reselect` for Redux, `useShallow` for Jotai in some configurations, and `useMemo` with a custom comparator in vanilla React.

Key Code / CLI Example
bun add zustand
⚠️Common Pitfall & Production Gotcha

- **Forgetting `useShallow` after upgrading to v5.** Zustand v4 happily re-rendered on every selector call; v5 uses `Object.is` by default and surfaces wrapper-object selectors as `Maximum update depth exceeded`. If you see the error after upgrading, the first place to look is every selector that returns a freshly built object or array. - **Expecting `shallow` to deep-compare nested objects.** `shallow({ a: { b: 1 } }, { a: { b: 1 } })` returns `false` because the nested `{ b: 1 }` references are different. If you need recursion, write a custom comparator or use `lodash.isEqual`. - **Passing `shallow` directly to `useStore`.** The vanilla `shallow` comparator expects to be called with `(currentSnapshot, nextSnapshot)`. The React hook is `useShallow`, which wraps a selector. Mixing them up triggers a TypeScript error such as `Type '(s: State) => Slice' is not assignable to type '(state: State) => Slice'`. - **Comparing objects whose prototypes differ.** `shallow(Object.create({}), {})` returns `false` even when the top-level fields would otherwise match. Zustand stores are plain objects (`Object.prototype`), so this rarely bites in practice, but it shows up when wrapping a store with `Object.create` to hide fields.

📝Comprehensive Study Notes & Mental ModelQuick Review
Expand NotesCollapse
Core Definition & Architectural Role

Imagine a coffee shop with a single host stand. Each customer walking in is checked against the guest list. Some days the host only checks names (`Object.is`); some days the host checks the whole party (`shallow` on a wrapper object). In the Zustand v5 world, the default host is strict (`Object.is`), and every selector inside `useStore` is on its own: each one has to remember to bring its own custom comparator (`useShallow`) or risk kicking off an infinite loop. `createWithEqualityFn` from `zustand/traditional` puts the host policy back at the door. You give the store one default comparator when you create it, and every selector read through the returned hook inherits that comparator automatically. You stop wrapping every selector with `useShallow`; you stop hand-rolling comparators at every call site. The comparator lives at the store, the way the host policy lives at the stand.

🧠Under-The-Hood Mental Model

Two stores in the same app can carry two different comparators. A `useBookmarkStore` created with `shallow` is friendly to wrapper selectors; a `useMetricsStore` created with the default `Object.is` is strict. Each comparator reflects the shape of the data the store owns. `createWithEqualityFn` lets you declare that policy once, at the store, instead of repeating it at every `useShallow` call. You will see this pattern in Zustand shops that bundle many stores: each one picks the comparator that matches its data shape, and consumers do not need to know which comparator is in use. The same idea shows up in Reselect for Redux, in `useSyncExternalStoreWithSelector` for low-level external stores, and in `useMemo` with a custom comparator in vanilla React.

Key Code / CLI Example
bun add zustand use-sync-external-store
⚠️Common Pitfall & Production Gotcha

- **Forgetting the peer dependency.** On a fresh Vite + React 18 setup, importing `zustand/traditional` without `use-sync-external-store` throws `Cannot find module 'use-sync-external-store/shim/...'` at build time. `bun add use-sync-external-store` once and it stops. - **Wrapping the store with `useShallow` anyway.** Once the comparator lives in the store, wrapping the selector in `useShallow` is redundant and clutters the call site. Either pick `createWithEqualityFn(..., shallow)` or pick `create` + `useShallow` per call site, not both. - **Expecting `shallow` to deep-compare nested objects.** The same rule from the previous chapter applies here. `shallow({ a: { b: 1 } }, { a: { b: 1 } })` returns `false`. The store-level comparator changes nothing about what `shallow` itself walks. - **Mixing `createWithEqualityFn` with `subscribeWithSelector` and the old v4 `subscribe(selector, listener)` overload.** v5 reorganised subscriptions; the selector overload now lives behind the `subscribeWithSelector` middleware. If you want to subscribe externally with a selector, opt in explicitly.

📝Comprehensive Study Notes & Mental ModelQuick Review
Expand NotesCollapse
Core Definition & Architectural Role

You have met the pieces already: `create`, selectors, `set`, `combine`, `shallow`. A game is where they stop being isolated facts and start being an architecture. Tic-tac-toe is small enough to hold in your head and rich enough to force every real decision a store faces: what to store, what to derive, how to keep a move immutable, and how to add a feature (time travel) without rewriting the model. The rule that carries this whole chapter: **store the minimum, derive the rest.** Every value you can compute from another value is a value that can drift out of sync. The game ends with exactly two stored fields.

🧠Under-The-Hood Mental Model

This is the shape of nearly every real Zustand store: a small stored core, derived values computed in render, immutable updates, and middleware added only where it pays off. Time travel is a stand-in for undo/redo, which you will build for real in an editor, a form wizard, or a drawing tool. The immutability habit that makes it cheap is the same habit React's reconciler depends on to detect changes at all.

Key Code / CLI Example
type Player = "X" | "O";
type SquareValue = Player | null;
type BoardState = SquareValue[];

function Square({
  value,
  onSquareClick,
}: {
  value: SquareValue;
  onSquareClick: () => void;
}) {
  return (
    <button className="square" onClick={onSquareClick}>
      {value}
    </button>
  );
}
⚠️Common Pitfall & Production Gotcha

An earlier draft of this game stored `xIsNext` as a boolean and flipped it on every move. Core Definition & Architectural Role

Think of a Zustand store as a package moving down a conveyor belt. Each piece of middleware is a station that can stamp the package before it reaches you. Most stations leave the contents alone: a logger prints what went by, but the box that comes out the far end holds exactly what went in. Other stations open the box and add something. `persist` bolts on a `persist` API. `devtools` wires in a time-travel connection. `redux` swaps the whole update mechanism for a `dispatch`. When a station changes what the box contains, the label on the box has to change too, or the person unpacking it reaches for a field that TypeScript swears isn't there. A **higher-kinded mutator** is how Zustand keeps the label honest. It is a type-level record that travels alongside the store, saying "after this middleware runs, the store also has `.persist`", or "…also has `.foo`". You rarely write one from scratch. You meet them the moment you type a `StateCreator` for a slice, and you must write one if you author middleware that attaches anything to the store object.

🧠Under-The-Hood Mental Model

You will not write a custom mutator most weeks. You *will* read these tuples constantly: every time you split a store into slices, type a store that stacks `devtools` + `persist` + `immer`, or debug why `set`'s third argument stopped compiling. Knowing that `Mis` shapes the tools you receive and `Mos` advertises what you add turns those cryptic `StateCreator<S, [['zustand/devtools', never]], []>` signatures into something you can write from memory. When you do author middleware, higher-kinded mutators are the difference between a middleware that lies about its store and one whose consumers get autocomplete for the fields it attaches. The bug class they prevent is the worst kind: code that type-checks but reaches for `store.persist` (or a devtools label, or an `immer` draft) that the types quietly stripped away, only to fail at runtime in production.

Key Code / CLI Example
import type { StateCreator, StoreMutatorIdentifier } from "zustand";

type Logger = <
  T,
  Mps extends [StoreMutatorIdentifier, unknown][] = [],
  Mcs extends [StoreMutatorIdentifier, unknown][] = [],
>(
  creator: StateCreator<T, Mps, Mcs>,
  name?: string,
) => StateCreator<T, Mps, Mcs>;

// The implementation is untyped internally, then cast to the public shape.
type LoggerImpl = <T>(
  creator: StateCreator<T, [], []>,
  name?: string,
) => StateCreator<T, [], []>;

const loggerImpl: LoggerImpl = (creator, name) => (set, get, store) => {
  const loggedSet: typeof set = (...args) => {
    set(...(args as Parameters<typeof set>));
    console.log(...(name ? [`${name}:`] : []), get());
  };
  return creator(loggedSet, get, store);
};

export const logger = loggerImpl as unknown as Logger;
⚠️Common Pitfall & Production Gotcha

- **Skipping the curried `create<T>()(...)` call.** Writing `create<T>((set) => ...)` (one call, explicit `T`) breaks middleware mutator inference; the extra `()` is a TypeScript workaround, not a style choice. Use `create<T>()((set) => ...)`. The same applies to `createStore<T>()(...)`. - **Forgetting to register a custom mutation in `StoreMutators`.** Without the `declare module "zustand/vanilla"` augmentation, `Mutate<StoreApi<T>, [["foo", A]]>` resolves to `never`, and `store.foo = bar` reports `Property 'foo' does not exist on type 'never'`. Register the identifier first. - **Augmenting the wrong module.** The `StoreMutators` interface is declared in `zustand/vanilla`. Augment that path (`declare module "zustand/vanilla"`), not a re-export, or the merge silently does nothing. - **Dropping the caller's `Mps`/`Mcs` on pass-through middleware.** Typing a logger as `StateCreator<T, [], []> => StateCreator<T, [], []>` erases every mutation from stores it wraps. Downstream, `set`'s devtools label or the `persist` API disappears. Thread `Mps`/`Mcs` through even when your middleware adds nothing. - **Assuming `combine` needs the curried form.** `combine(initialState, creator)` infers the full store type on its own, so `create(combine(...))` works without `create<T>()`. Its trade-off is that `get()` inside the creator only sees the initial-state half, not the actions you are adding.

Core Definition & Architectural Role

A traffic light is a state machine. Three bulbs, six transitions, no side effects. The state moves forward on a `tick` action, jumps to red on an `emergency` action, and resets on a `reset` action. The same rules apply every time the inputs come in, in the same order, and the same output comes out. That is a reducer. `useReducer` is React's built-in state-machine hook. It hands you a function `(state, action) => newState` and gives you back a `dispatch` to send actions into it. Every state change in a reducer-based component flows through one function, which means you can read the whole app's transition logic in a single place.

🧠Under-The-Hood Mental Model

The reducer pattern shows up wherever state has more than one kind of update and the updates have non-trivial payloads. Forms with nested fields, multi-step wizards, paginated lists with filters and sort orders, optimistic updates from server responses, undo/redo stacks, and any feature flagging system that combines independent toggles all fit the pattern. You will meet the same shape in three different sizes:

Key Code / CLI Example
import { useReducer } from "react";

type State = { count: number };

type CounterAction =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "set"; value: number }
  | { type: "reset" };

const initialState: State = { count: 0 };

function reducer(state: State, action: CounterAction): State {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };
    case "decrement":
      return { count: state.count - 1 };
    case "set":
      return { count: action.value };
    case "reset":
      return { count: 0 };
    default: {
      const exhaustive: never = action;
      return exhaustive;
    }
  }
}

export function Counter() {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <div>
      <p>Count: {state.count}</p>
      <button type="button" onClick={() => dispatch({ type: "increment" })}>
        +1
      </button>
      <button type="button" onClick={() => dispatch({ type: "decrement" })}>
        -1
      </button>
      <button type="button" onClick={() => dispatch({ type: "set", value: 10 })}>
        set 10
      </button>
      <button type="button" onClick={() => dispatch({ type: "reset" })}>
        reset
      </button>
    </div>
  );
}
⚠️Common Pitfall & Production Gotcha

- **Mutating `state` inside the reducer.** `state.count += 1` returns the same object reference. React may bail out of the re-render because `Object.is(prev, next)` is true, and any other code that held a reference to the old state now sees the wrong value. The error React surfaces in development is `Cannot assign to read only property 'count' of object` if you mutated under `strict mode`, or simply a missing UI update otherwise. // Right case "increment": return { count: state.count + 1 }; ``` - **Forgetting the `never` exhaustive check.** Without `const exhaustive: never = action;` in the `default` branch, adding a fifth action variant to the union compiles fine and silently falls through to the `default`, which then returns `undefined`. TypeScript with `noFallthroughCasesInSwitch` and a `never` assignment closes that gap. - **Using a loose action type.** `type Action = { type: string }` defeats the whole pattern: `action.value` is always typed and you can `dispatch({ type: "incrementr" })` and never know it. Keep the `type` field as a string literal in every variant. - **Initializing expensive state inline.** `useReducer(reducer, expensiveComputation())` runs the computation on every render even though only the first value is used. Pass the third argument as a lazy initializer: `useReducer(reducer, initialArg, init)`. The initializer runs once at mount.

- **Mutating `state` inside the reducer.** `state.count += 1` returns the same object reference. React may bail out of the re-render because `Object.is(prev, next)` is true, and any other code that held a reference to the old state now sees the wrong value. The error React surfaces in development is `Cannot assign to read only property 'count' of object` if you mutated under `strict mode`, or simply a missing UI update otherwise. // Right case "increment": return { count: state.count + 1 }; ``` - **Forgetting the `never` exhaustive check.** Without `const exhaustive: never = action;` in the `default` branch, adding a fifth action variant to the union compiles fine and silently falls through to the `default`, which then returns `undefined`. TypeScript with `noFallthroughCasesInSwitch` and a `never` assignment closes that gap. - **Using a loose action type.** `type Action = { type: string }` defeats the whole pattern: `action.value` is always typed and you can `dispatch({ type: "incrementr" })` and never know it. Keep the `type` field as a string literal in every variant. - **Initializing expensive state inline.** `useReducer(reducer, expensiveComputation())` runs the computation on every render even though only the first value is used. Pass the third argument as a lazy initializer: `useReducer(reducer, initialArg, init)`. The initializer runs once at mount.
